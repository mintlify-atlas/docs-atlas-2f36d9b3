Kairo uses PostgreSQL 14+ as its primary data store, managed through Supabase. All schema definitions, migrations, access policies, and test data live in the `database/` directory.

## Database engine

Kairo is designed for **PostgreSQL 14+** via Supabase. Self-hosted PostgreSQL works too — set `DB_SSL=false` in `backend-node/.env` and provide connection details via the `DB_*` variables or a `DATABASE_URL` connection string. See [Environment variables](/self-hosting/environment-variables) for configuration details.

## Running the initial schema

<Steps>
  <Step title="Open the SQL editor">
    In the Supabase dashboard, navigate to **SQL Editor**. Alternatively, connect directly using `psql` or any PostgreSQL client.
  </Step>

  <Step title="Run schema.sql">
    Paste or import the full contents of `database/schema.sql` and execute it. The script creates all enum types, tables, indexes, and views.

    ```bash
    psql "$DATABASE_URL" -f database/schema.sql
    ```
  </Step>

  <Step title="Run rls_policies.sql">
    Apply Row Level Security policies to enforce per-role data access:

    ```bash
    psql "$DATABASE_URL" -f database/rls_policies.sql
    ```
  </Step>

  <Step title="Run migrations">
    Apply migration files in order. Always run them sequentially:

    ```bash
    psql "$DATABASE_URL" -f database/migrations/001_add_clans_and_priority_and_notifications.sql
    psql "$DATABASE_URL" -f database/migrations/002_add_raw_answers_to_soft_skills.sql
    psql "$DATABASE_URL" -f database/migrations/005_create_user_profiles.sql
    ```
  </Step>

  <Step title="(Optional) Load seed data">
    For development and testing, load sample users, modules, and progress data:

    ```bash
    psql "$DATABASE_URL" -f database/seeds/users.sql
    ```

    This inserts 8 users (2 Team Leaders, 6 Coders across 3 clans), 6 bootcamp modules, soft skills assessments, and academic progress records.
  </Step>
</Steps>

## Enum types

The schema defines 8 custom PostgreSQL enum types used throughout the tables:

```sql
CREATE TYPE role_enum AS ENUM ('coder', 'tl');
CREATE TYPE learning_style_enum AS ENUM ('visual', 'auditory', 'kinesthetic', 'mixed');
CREATE TYPE activity_type_enum AS ENUM ('guided', 'semi_guided', 'autonomous');
CREATE TYPE feedback_type_enum AS ENUM ('weekly', 'activity', 'general');
CREATE TYPE risk_level_enum AS ENUM ('low', 'medium', 'high');
CREATE TYPE report_target_enum AS ENUM ('coder', 'clan', 'cohort');
CREATE TYPE ai_agent_enum AS ENUM ('learning_plan', 'report_generator', 'risk_detector');
CREATE TYPE priority_level_enum AS ENUM ('low', 'medium', 'high');
```

## Schema overview

The schema contains 14 tables organized across four functional areas:

### Users and assessments

| Table | Description |
|---|---|
| `users` | All platform users. The `role` column (`coder` or `tl`) controls access throughout the system. `clan_id` identifies which clan a coder belongs to (Turing, Tesla, or McCarthy). |
| `soft_skills_assessment` | One-per-coder record of soft skills scores (autonomy, time management, problem solving, communication, teamwork, 1–5 scale) and learning style. |

### Academic content

| Table | Description |
|---|---|
| `modules` | Bootcamp modules (e.g., Fundamentos de Python, JavaScript, Backend con Node.js). Each module has a `total_weeks` count. |
| `topics` | Individual topics within a module, each tagged with a `category` (e.g., Conceptos, Avanzado). |
| `moodle_progress` | Per-coder, per-module academic progress: current week, completed weeks (JSONB array), struggling topics, and average score. |
| `coder_struggling_topics` | Many-to-many join between coders and topics where they report difficulty. |

### Personalized learning plans

| Table | Description |
|---|---|
| `complementary_plans` | AI-generated learning plans (the "6 Cards"). Each plan has a `priority_level` (high, medium, or low) and stores the full `plan_content` as JSONB. |
| `plan_activities` | Individual daily activities within a plan. Each activity has a `day_number`, `activity_type` (guided, semi_guided, or autonomous), and `estimated_time_minutes`. |
| `activity_progress` | Tracks whether a coder has completed each activity. Stores reflection text and time spent. |
| `evidence_submissions` | Files and links submitted by coders as evidence of activity completion. |

### Communication and analytics

| Table | Description |
|---|---|
| `tl_feedback` | Messages sent by Team Leaders to coders. `is_read` drives the notification bell indicator (unread = red dot). |
| `risk_flags` | Automatically detected risk alerts for coders with low scores or low autonomy. Can be resolved by a TL. |
| `ai_reports` | Executive reports generated by the AI for Team Leaders, scoped to a `coder`, `clan`, or `cohort`. |
| `ai_generation_log` | Audit trail of every AI call: input/output payloads, model name, execution time, and success status. |

## Database views

The schema includes two views that power the main dashboards:

### `v_coder_dashboard`

Aggregates a coder's progress into a single row per coder. Returns:

- Soft skills scores (autonomy, time management, learning style)
- Current module, week, and average Moodle score
- Total activities in the active plan and how many have been completed
- Completion percentage (rounded to 2 decimal places)

This view is used to populate the Coder dashboard card.

### `v_coder_risk_analysis`

Calculates the risk level for each coder by comparing autonomy scores and academic performance. Returns:

- Stored `current_risk_level` from `risk_flags`
- A `calculated_risk_level` derived from the rule: autonomy ≤ 2 **and** average score < 70 → `high`; either condition alone → `medium`; otherwise → `low`
- Activity counts for the active plan

Team Leaders use this view to identify at-risk coders before reviewing individual profiles.

## Row Level Security

All 14 tables have RLS enabled. `database/rls_policies.sql` defines the access rules:

- **Coders** can only read and write their own rows (their own profile, progress, plans, activities, feedback, and evidence).
- **Team Leaders** can read all coder data. They are the only role that can create modules, topics, plans, and send feedback.
- **Modules and topics** are readable by everyone, but only TLs can create or edit them.
- The `ai_reports` and `ai_generation_log` tables are restricted to TLs only.

<Note>
  RLS policies use `auth.uid()` and `auth.jwt()->>'role'` — both are Supabase built-ins. If you connect via the service role key (as the Python backend does), RLS is bypassed entirely, which is intentional for server-side AI operations.
</Note>

## Migrations

Migration files are stored in `database/migrations/` and named with a numeric prefix for ordering:

| File | Description |
|---|---|
| `001_add_clans_and_priority_and_notifications.sql` | Adds `clan_id` to `users`, `priority_level` to `complementary_plans`, and `is_read` to `tl_feedback`. |
| `002_add_raw_answers_to_soft_skills.sql` | Adds a `raw_answers` JSONB column to `soft_skills_assessment` for storing the original diagnostic responses. |
| `005_create_user_profiles.sql` | Creates the user profiles structure. |

Run migrations in numeric order. All migration scripts use `ADD COLUMN IF NOT EXISTS` and `CREATE TYPE IF NOT EXISTS`, so they are safe to re-run on an already-migrated schema.

## Seed data

The `database/seeds/users.sql` script populates the database with test data for development:

- **8 users**: 2 Team Leaders (María García, Carlos Rodríguez) and 6 Coders distributed across three clans — Turing (Juan, Ana), Tesla (Pedro, Sofía), and McCarthy (Luis, María)
- **6 bootcamp modules**: Python, HTML/CSS, JavaScript, Bases de Datos, Backend con Node.js, React
- **Soft skills assessments** for all 6 coders, with varied scores to simulate at-risk (Luis, Juan) and high-performing (Sofía) cases
- **Academic progress** across modules, with scores ranging from 58 to 95
- **Struggling topics** linked to the coders most likely to trigger risk detection

To load seeds:

```bash
psql "$DATABASE_URL" -f database/seeds/users.sql
```

Verify after loading:

```sql
SELECT COUNT(*) FROM users;                    -- 8
SELECT COUNT(*) FROM modules;                  -- 6
SELECT COUNT(*) FROM soft_skills_assessment;   -- 6
```

## Connection settings

The Node.js service connects to PostgreSQL via a connection pool (`pg.Pool`). The pool is configured with:

- **Max connections**: 10
- **Idle timeout**: 30 seconds
- **Connection timeout**: 30 seconds
- **Query timeout**: 30 seconds

For Supabase, use the **Transaction pooler** connection string as `DATABASE_URL`. The format is:

```
postgresql://postgres.PROJECT_ID:PASSWORD@aws-0-REGION.pooler.supabase.com:5432/postgres
```

The `DB_USER` must be formatted as `postgres.PROJECT_ID` when using the Supabase pooler. If you see a `XX000: Tenant or user not found` error, verify the user format and ensure SSL is enabled.

## Session table

<Note>
  The `session` table (used by `connect-pg-simple` for server-side session storage) is **not** included in `schema.sql`. It is created automatically the first time the Node.js server starts, because `connect-pg-simple` is configured with `createTableIfMissing: true`. You do not need to create it manually.
</Note>
