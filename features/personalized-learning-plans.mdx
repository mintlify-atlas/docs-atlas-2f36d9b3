---
title: "Personalized learning plans"
description: "AI-generated adaptive 4-week study plans tailored to each Coder's performance and learning style."
---

A personalized learning plan is a 4-week study program generated by Kairo's AI engine for each individual Coder. The plan surfaces the highest-priority topics for that Coder at that moment, structures daily work to fit their learning style, and adapts based on their academic progress and soft skills profile.

## What a plan contains

Each plan centers on **6 focus cards** distributed across three priority tiers:

| Priority | Cards | Purpose |
|---|---|---|
| High | 2 | Topics the Coder is actively struggling with |
| Medium | 2 | Topics that need reinforcement |
| Low | 2 | Exploratory or enrichment topics |

Each focus card maps to one or more **plan activities** stored in the `plan_activities` table. Every activity has:

- `title` — short, actionable description
- `description` — full task instructions
- `estimated_time_minutes` — expected time investment
- `skill_focus` — which soft skill the activity targets (e.g., `autonomy`, `problem_solving`)
- `activity_type` — one of `guided`, `semi_guided`, or `autonomous`
- `day_number` — which of the 20 plan days this activity falls on

A full plan runs **20 working days** (4 weeks × 5 days). Each day contains one or more activities totaling roughly 60–90 minutes of focused work.

## Plan types

Kairo supports two plan generation modes controlled by the `plan_type` field:

| Plan type | Input data | When to use |
|---|---|---|
| `interpretive` | Soft skills assessment only | Coder is new or has no Moodle progress data |
| `analytical` | Soft skills + Moodle score, current week, and struggling topics | Coder has existing academic data in Moodle |

The `interpretive` type produces a plan based entirely on the Coder's self-assessed competencies and learning style. The `analytical` type overlays Moodle performance data — including `average_score`, `current_week`, and `struggling_topics` — to produce a more targeted remediation plan.

<Note>
  If no soft skills assessment exists for the Coder, plan generation fails with HTTP 400. The assessment must be completed during onboarding before a plan can be generated. See [Soft skills assessment](/features/soft-skills-assessment).
</Note>

## How plans are generated

<Steps>
  <Step title="Coder requests a plan">
    The Coder triggers plan generation by calling `POST /api/coder/plan/request`. The Node.js gateway reads the Coder's `current_module_id` and fires a request to the Python AI microservice asynchronously — the HTTP response returns immediately with `{ "requested": true }` so the frontend is not blocked.
  </Step>

  <Step title="Previous plan is deactivated">
    Before generating a new plan, the service calls `db_manager.deactivate_plans(coder_id)`, which sets `is_active = false` on all existing plans for that Coder. Only one plan is active at a time.
  </Step>

  <Step title="Context is assembled">
    The AI engine fetches the Coder's soft skills assessment, module details, weeks, and topics from the database. For `analytical` plans, Moodle progress data (`average_score`, `struggling_topics`, `weeks_completed`) is also fetched automatically if not provided in the request.
  </Step>

  <Step title="LLM generates the plan">
    The assembled context is sent to Groq's `llama-3.3-70b-versatile` model (or the model configured in `MODEL_NAME`). The LLM returns a structured JSON plan with focus cards and daily activities.
  </Step>

  <Step title="Plan and activities are persisted">
    The plan is saved to `complementary_plans` with `is_active = true`. Individual activities are written to `plan_activities` so TLs can see real-time activity data per Coder.
  </Step>

  <Step title="Generation is logged">
    A row is inserted into `ai_generation_log` recording the agent type (`plan_generator`), input payload, output plan ID, execution time in milliseconds, and whether the plan succeeded or fell back.
  </Step>
</Steps>

## GeneratePlanRequest schema

The Python microservice accepts the following fields at `POST /generate-plan`:

| Field | Type | Default | Description |
|---|---|---|---|
| `coder_id` | `int` | required | ID of the Coder receiving the plan |
| `module_id` | `int` | required | ID of the current bootcamp module |
| `plan_type` | `str` | `"interpretive"` | `"interpretive"` or `"analytical"` |
| `current_week` | `int` | `1` | Coder's current week in the module |
| `average_score` | `float` | `0.0` | Moodle average score (0–100) |
| `struggling_topics` | `list[str]` | `[]` | Topics the Coder is struggling with |
| `weeks_completed` | `list[dict]` | `[]` | Summary of completed weeks from Moodle |

For `analytical` plans, if `average_score` is `0.0` and `weeks_completed` is empty, the service automatically fetches the latest Moodle progress record from the database.

## Plan lifecycle

Plans are stored in the `complementary_plans` table with the following lifecycle fields:

```sql
CREATE TABLE complementary_plans (
  id                     SERIAL PRIMARY KEY,
  coder_id               INT NOT NULL,
  module_id              INT NOT NULL,
  plan_content           JSONB NOT NULL,
  priority_level         priority_level_enum DEFAULT 'medium',
  soft_skills_snapshot   JSONB,
  moodle_status_snapshot JSONB,
  is_active              BOOLEAN DEFAULT TRUE,
  generated_at           TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

`soft_skills_snapshot` and `moodle_status_snapshot` capture the exact state of the Coder's profile at generation time. This means the plan always reflects the conditions under which it was created, even if the Coder's data changes later.

## Daily completion flow

Coders mark a day as complete by calling:

```
POST /api/coder/plan/:planId/day/:day/complete
```

The server validates that `day` is between 1 and 20, then updates the `completed_days` JSONB field on the plan:

```json
{
  "1": { "completedAt": "2026-03-15T10:00:00.000Z" },
  "2": { "completedAt": "2026-03-16T11:30:00.000Z" }
}
```

Completing a day also writes records to `activity_progress` for each activity in that day and awards Kairo score points. Completing all 20 days awards a bonus.

## Evidence submission

Coders can attach proof of completed activities by uploading a file or a link. Evidence is stored in the `evidence_submissions` table:

```sql
CREATE TABLE evidence_submissions (
  id           SERIAL PRIMARY KEY,
  activity_id  INT NOT NULL,
  coder_id     INT NOT NULL,
  file_url     TEXT,
  link_url     TEXT,
  description  TEXT,
  submitted_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

Each submission is tied to a specific `activity_id`. TLs can review evidence via the [TL dashboard](/features/tl-dashboard).
